FEEDS FORECAST — SUPABASE SCHEMA CLEANUP AUDIT
Date: 22 November 2026 (Asia/Singapore)

SCOPE AND CONFIDENCE
The connected Supabase REST OpenAPI schema exposed 17 tables and 175 columns.
live-schema.json contains the observed names and types; no row contents were read.
The application, SQL migrations and repairs were searched for references.
identifier-references.json is a lexical reference index, NOT proof that each
matching identifier refers to the same database column.
No database objects or records were changed during this audit.

REST metadata does not establish that every column is unused or that all
database objects are visible. Current functions, triggers, RLS, views, indexes,
external integrations, BI datasets and populated data need catalog verification.
Use verify-dependencies.sql in Supabase SQL Editor for read-only checks.
Historical migration references are not proof of current installed functions.

SUMMARY
1. categories.description is ALREADY ABSENT from the connected live schema.
   The Categories screen no longer selects, writes, searches or displays it.
   No Description-removal SQL is needed on this connected project.
2. No complete table is confirmed unused. Keep all 17 until catalog checks finish.
3. actual_import_staging.subregion is the strongest unused-column REVIEW candidate.
   The current volume-import pipeline does not read/write this text field; actual
   saved-record subregion_id is resolved from the salesperson assignment instead.
   Check installed functions, old uploads and other clients before dropping it.
4. asm/rsm text fields are possible later simplification candidates, NOT safe
   immediate drops. Current saved-record reads and optimistic edit checks use them.
5. Existing plural, snake_case table names are generally consistent. Avoid broad
   cosmetic renaming that would require changing many RPC and permission contracts.

UNUSED / LEGACY CANDIDATES
actual_import_staging.subregion
  Review candidate. No use in the current volume-import page's selected staging
  fields, spreadsheet mapping, row editor or staging payload. An old text field is
  not equivalent to actuals.subregion_id, which remains necessary for visibility.

budgets.asm, budgets.rsm, actuals.asm, actuals.rsm
  NOT removable as-is. components/volume-import-page.tsx explicitly selects them.
  lib/saved-volume-records.ts includes them in original snapshots and conditional
  update checks. The customer-volume SQL function also compares these fields.
  Existing import uploads set staging asm/rsm to null and current import payloads
  use kam, so a future coordinated removal may be useful after profiling data.

budget_import_staging.asm/rsm, actual_import_staging.asm/rsm
  NOT removable as-is. They remain in the current staging SELECT/type/insert
  contracts, even though current uploads initialize them to null. Remove those
  contracts first and verify no external uploader still populates these fields.

actuals.updated_at, customers.updated_at, staging created_at fields
  Retain pending trigger/function/external integration checks. Timestamps may be
  managed on the server or used for audit and ordering even when not shown in UI.

DO NOT DELETE THESE JUST BECAUSE THEY LOOK DUPLICATED OR HIDDEN
forecasts.user_id versus submitted_by/endorsed_by/approved_by/returned_by:
  Distinct ownership and workflow actors. These are not interchangeable.
forecasts.forecast versus volume; products.weight:
  Quantity and 50kg-equivalent volume are distinct; weight drives conversion.
actuals.actual_date versus year/month:
  Live Actual tables already omit year/month; the app derives them from the date.
  Budget year/month remain necessary, including month=NULL annual budgets.
category_id versus product_id; region_id versus subregion_id:
  Existing reporting, access scopes and update contracts depend on them. A
  normalization refactor is different from deleting an unused column.
users.must_change_password, dashboard_type, role, position, region_id, subregion_id:
  Active login, dashboard, permission and visibility features.
user_permissions.is_default / can_export / can_import:
  Active permission-default and feature checks.
week_locks override columns and forecast_week_policy / forecast_week_audit:
  Automatic scheduling, overrides and audit history use these through SQL/RPCs.
audit_logs.actor_id and workflow timestamps:
  Server-side use exists despite no direct app identifier references for some.

SAFE IMPLEMENTATION ORDER
1. Run the supplied read-only catalog audit and inspect BI/ETL/external clients.
2. Export schema and back up affected data before any destructive migration.
3. For a rename, update app queries/types, API payloads, RPC return signatures,
   SQL function source, policies/triggers, exports/templates and dependent reports
   together. A PostgreSQL rename alone does not rewrite every SQL string.
4. For deletion candidates, remove app and SQL dependencies before dropping the
   column. An all-null profile is insufficient evidence by itself.
5. Apply one change in UAT, then test all role scopes, imports, record edits,
   approvals, dashboard, exports and week locks. Do not use DROP ... CASCADE.
6. Reload PostgREST schema after an approved schema migration and redeploy the
   matching application. No destructive migration is included in this report.
